Java4Shell Lab: JVM Exposure Triage and Executive Reporting

A terminal-first Java4Shell assessment for authorized pentesters: runtime inventory, AVX-512 prerequisites, identity-risk analysis and management-ready reporting.

Objective

This is a local, read-only triage, not a remote exploit. It helps an authorized pentester or platform engineer determine whether a host has Java4Shell’s hardware prerequisites, capture the default Java runtime’s details, and produce a structured report. It deliberately avoids malformed Base64 payloads that could crash or corrupt a JVM.

$ python3 scripts/java4shell_assess.py --out java4shell-report
Finding: assessed x86 path excluded / prerequisites found / review required
Application risk: not determined (application not tested)
Reports: java4shell-report.md, java4shell-report.json

Run the assessment

From the blog source root, use Python 3.9+ (standard library only):

python3 scripts/java4shell_assess.py --out java4shell-report
python3 -m json.tool java4shell-report.json >/dev/null
cat java4shell-report.md

The full runnable script is included at scripts/java4shell_assess.py in the project archive. The updated script supports macOS (Intel and Apple Silicon), Windows 11, and Linux (including Ubuntu 24.04 and 26.04). On Windows x86-64, AVX-512 detection remains UNKNOWN unless separately corroborated; Apple Silicon is reported as not applicable to the x86 vector path. It also inspects java -version and relevant default JVM flags. It now provides a CPU-path applicability finding rather than always reporting INVENTORY_ONLY. It does not enumerate all deployed JVMs, establish patch status from the version alone, or determine application exploitability.

Manual checks to corroborate

# Linux CPU prerequisites: all four flags are needed for the reported path
grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(avx512f|avx512bw|avx512vbmi|bmi2)$'

# Default Java executable; actual application runtimes may differ
command -v java
java -version

# Linux: list running Java processes (permissions may limit visibility)
ps -eo pid,args | grep '[j]ava'

# Java runtime flags (for an authorized process, with jcmd available)
jcmd <PID> VM.flags

The jcmd command requires replacing <PID> with a real process ID. Use jcmd <PID> VM.command_line to identify the running JVM’s launch arguments when authorized. Do not confuse the host’s default Java version with the one embedded in an application container.

Controlled mitigation validation

  1. Record the running JVM build, CPU capabilities, container image digest, and whether attacker-controlled Base64 reaches java.util.Base64.Decoder.
  2. In an isolated staging environment, patch to a vendor-confirmed fixed runtime and restart the service; rebuild images where necessary.
  3. When patching is temporarily unavailable, test -XX:-UseBASE64Intrinsics or the x86-only -XX:UseAVX=2 workaround; confirm the running JVM accepted the setting and monitor performance.
  4. Verify that the authentication service still issues and rejects synthetic test tokens as expected; check that service accounts have minimum necessary permissions.
  5. Re-run the inventory script, attach the vendor build evidence and service test results, and document closure separately. A clean inventory report is not proof of exploit resistance.

Exploit-code reference and safe testing boundary

The Calif research publication describes the heap-corruption mechanism and publicly discusses a proof of concept. The publicly described demonstration is not a universal RCE exploit. Review the research in an isolated environment; avoid sending crash-inducing malformed inputs to production identity systems. A generic remote HTTP probe is not a reliable Java4Shell detector because the vulnerable code path is application-dependent.

This is a non-exploitative prerequisite and runtime assessment, not a confirmation of application exploitability.
