Security-Key-First WebAuthn Lab

An interactive FIDO2 registration and authentication experiment for security keys and compatible smart cards, hosted entirely on GitHub Pages.

This is a hands-on companion to Making Security-Key Enrollment Less Painful in Modern Browsers. The objective is to measure how much of a physical security-key journey can be simplified without bypassing browser or authenticator security controls.

The experiment runs as a standalone HTML page on HTTPS GitHub Pages. It creates real WebAuthn credentials on supported authenticators and verifies subsequent signed assertions locally using the Web Crypto API. No server, account service or external dependency is required.

New in the updated lab: an external-security-key preference switch, discoverable/passwordless authentication, browser capability inspection, and live ceremony progress. Safari and Chrome may render different browser-owned prompts, and a FIDO2-enabled smart card may need PIN and user-presence confirmation.

For the most reliable experience, launch the standalone security-key lab. Embedded WebAuthn may be restricted by browser policies, especially in Safari. Enroll and authenticate on the same origin and browser profile; the local credential registry is not synchronized between Safari and Chrome.

Important: This is a local cryptographic demonstration, not production authentication. Credentials and public keys are stored in this browser’s local storage, registration attestation is not verified by a trusted server, and challenges are generated client-side. Browser-local state can be altered by anyone controlling the browser. Do not use the demo to protect an account, issue trusted credentials or establish enterprise assurance.

Open the lab in its own window

Test plan

  1. Open the standalone lab on HTTPS (or http://localhost for local development).
  2. Insert a FIDO2 security key or a compatible smart card and reader; choose a test username.
  3. Choose Enroll security key and complete the browser’s prompts.
  4. Choose Authenticate to produce and locally verify a signed assertion using the enrolled public key.
  5. Compare Safari with Chrome or Edge on the same authenticator, noting how the browser interprets the security-key hint and cross-platform selection.

The default configuration prefers a security key, cross-platform attachment, and optional PIN/UV (preferred). Turn on Require PIN / user verification when testing a higher-assurance policy. Requiring discoverable credentials is also optional because many cards have limited resident credential storage.

Limitations

The browser chooses its own dialogs. A smart card needs a functioning FIDO2 application and reader path; PIV/PKI alone is insufficient. The demo cannot attest that a particular physical card model was used. Clearing browser storage removes the local registration record but does not erase the credential from the security key.
