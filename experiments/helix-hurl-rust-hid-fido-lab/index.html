Helix, Hurl, and Rust: A Terminal-First Approach to API Testing

Edit with Helix, test with Hurl, and automate with Rust: a reproducible identity API lab using OAuth, SCIM, and FIDO device binding.

Lab objective: Authenticate an integration client, create a test user, create and bind a pending FIDO device, then verify the association. No password authenticator is created. A pending device is not an enrolled passkey.

Three tools, one repeatable workflow

A terminal-first approach is not about avoiding graphical interfaces. It is about making the steps of an API test visible, reviewable, and repeatable. A collection of requests is useful; a project that another engineer can clone, run, and validate is better.

This experiment combines three focused tools:

  • Helix — edit. Navigate and maintain plain-text API requests, Rust source, and project configuration without leaving the terminal.
  • Hurl — test. Send HTTP requests, capture response values, and assert expected behavior in readable .hurl files.
  • Rust — automate. Prepare unique test identities and orchestrate the same test sequence without duplicating Hurl’s HTTP functionality.

The test files can be committed to Git, reviewed as diffs, and reused in an authorized test environment. This builds on Helix: Making Editing Fun Again by moving from editing and isolated requests to a complete identity API lifecycle.

$ hx tests/provision-fido.hurl   # edit the HTTP workflow
$ cargo run                     # generate a unique test identity and run Hurl
[+] Running HID provisioning test with unique lab identity: terminal-lab-...
[+] SCIM FIDO pre-enrollment checks passed.

The output illustrates a successful configured-tenant run; it is not a captured live HID result.

The test case: identity provisioning with HID

We will use HID Authentication Service to make the workflow concrete: obtain an OAuth access token, create a user using SCIM, prepare a pending FIDO device, bind it to the new user, and verify the association. This is a lifecycle API test, not a simulation of the FIDO cryptographic ceremony.

Why HID Authentication Service?

The HID Authentication Service exposes an OpenID Connect/OAuth token endpoint and SCIM APIs for user and device lifecycle management. Its FIDO integration uses AT_FIDO for the authentication policy and DT_FIDO for the device type. For a device-binding-required workflow, a pending FIDO device can be created and assigned to a user before a genuine WebAuthn enrollment ceremony.

This distinction matters: we are preparing an identity for FIDO, not minting a security key through an API. A private key must be generated and held by a FIDO authenticator during the actual registration process.

[OAuth client_credentials] -> [SCIM Users POST]
                                      |
                                      v
                              [internal user ID]
                                      |
[SCIM Device POST: DT_FIDO/PENDING] -> [device ID]
                                      |
                                      v
                           [SCIM Device PUT: owner]
                                      |
                                      v
                          [SCIM Device GET: verify]
                                      |
                         [IdP WebAuthn enrollment]
                              (separate ceremony)

Install and configure

brew install helix hurl rustup
rustup default stable

cd examples/hid-fido-hurl-lab
mkdir -p .secrets
cp .env.example .secrets/hurl.env
chmod 600 .secrets/hurl.env
hx .secrets/hurl.env

Fill in the HID tenant host, tenant identifier, client ID and client secret. Use a test tenant and an API client explicitly authorized for user/device lifecycle operations. The client-credentials token endpoint is /idp/{tenant}/authn/token; the SCIM endpoints are under /scim/{tenant}/v2/.

The secrets file is excluded from Git. Do not paste tokens into logs or enable verbose HTTP tracing when working with live credentials.

The Hurl collection — documented and readable

The sequence deliberately uses the Device API for the pending FIDO device rather than pretending that a generic AT_FIDO authenticator POST registers a security key. The expected HTTP 200 on device creation and binding follows HID’s published FIDO integration examples; the user creation uses the SCIM HTTP 201 expectation.

# HID Authentication Service — FIDO device pre-enrollment lab
# Run ONLY against a test tenant with a privileged API client.
# Client secrets live in .secrets/hurl.env (mode 0600), never in Git.
# Each run uses a unique test_username and device_external_id from Rust.
# A pending device is NOT an enrolled passkey or usable FIDO credential.

# 01 / Machine-to-machine OAuth token (HID OpenID token endpoint)
POST {{base_url}}/idp/{{tenant}}/authn/token
Content-Type: application/x-www-form-urlencoded
[BasicAuth]
{{client_id}}: {{client_secret}}
[Form]
grant_type: client_credentials

HTTP 200
[Captures]
access_token: jsonpath "$.access_token"
[Asserts]
jsonpath "$.access_token" exists
jsonpath "$.token_type" == "Bearer"

# 02 / Provision an isolated test identity through SCIM
POST {{base_url}}/scim/{{tenant}}/v2/Users?api-version=11
Authorization: Bearer {{access_token}}
Content-Type: application/scim+json
Accept: application/scim+json
{
  "schemas": ["urn:ietf:params:scim:schemas:core:2.0:User"],
  "userName": "{{test_username}}",
  "name": {"givenName": "Terminal", "familyName": "Lab"},
  "active": true
}

HTTP 201
[Captures]
user_id: jsonpath "$.id"
[Asserts]
jsonpath "$.id" exists
jsonpath "$.userName" == "{{test_username}}"

# 03 / Create a pending FIDO device; this does NOT generate a private key
# HID FIDO integration documentation shows HTTP 200 for Device creation.
POST {{base_url}}/scim/{{tenant}}/v2/Device?api-version=11
Authorization: Bearer {{access_token}}
Content-Type: application/scim+json
Accept: application/scim+json
{
  "schemas": ["urn:hid:scim:api:idp:2.0:Device"],
  "externalId": "{{device_external_id}}",
  "type": "DT_FIDO",
  "status": {"status": "PENDING", "neverExpires": true}
}

HTTP 200
[Captures]
device_id: jsonpath "$.id"
[Asserts]
jsonpath "$.id" exists
jsonpath "$.type" == "DT_FIDO"
jsonpath "$.status.status" == "PENDING"

# 04 / Bind the pending device to the newly created SCIM user
# This follows HID's documented PUT /Device/{id} assignment operation.
PUT {{base_url}}/scim/{{tenant}}/v2/Device/{{device_id}}?api-version=11
Authorization: Bearer {{access_token}}
Content-Type: application/scim+json
Accept: application/scim+json
{
  "schemas": ["urn:hid:scim:api:idp:2.0:Device"],
  "id": "{{device_id}}",
  "type": "DT_FIDO",
  "status": {"status": "PENDING", "active": false},
  "owner": {"value": "{{user_id}}"}
}

HTTP 200
[Asserts]
jsonpath "$.id" == "{{device_id}}"
jsonpath "$.owner.value" == "{{user_id}}"
jsonpath "$.status.status" == "PENDING"

# 05 / Read back the binding to verify persistence
GET {{base_url}}/scim/{{tenant}}/v2/Device/{{device_id}}?api-version=11
Authorization: Bearer {{access_token}}
Accept: application/scim+json

HTTP 200
[Asserts]
jsonpath "$.id" == "{{device_id}}"
jsonpath "$.owner.value" == "{{user_id}}"
jsonpath "$.type" == "DT_FIDO"

Hurl’s [Captures] blocks carry the access token, user ID and device ID to later requests. [Asserts] stop the test when the response does not match the expected resource state. If an assertion fails, inspect the tenant’s API version and permissions rather than weakening the check to accept any HTTP response.

Rust as the thin runner

I do not need another HTTP framework for this experiment. Rust simply gives each run a unique identity and launches Hurl. That avoids conflicts from repeatedly creating the same SCIM username.

use std::{env, path::Path, process::{Command, ExitCode}, time::{SystemTime, UNIX_EPOCH}};

fn main() -> ExitCode {
    let config = Path::new(".secrets/hurl.env");
    if !config.is_file() {
        eprintln!("Missing .secrets/hurl.env; copy .env.example and edit it.");
        return ExitCode::FAILURE;
    }
    let now = SystemTime::now().duration_since(UNIX_EPOCH).expect("clock").as_millis();
    let suffix = format!("{}-{}", now, std::process::id());
    let username = format!("terminal-lab-{}", suffix);
    let device = format!("fido-lab-{}", suffix);
    println!("[+] Running HID provisioning test with unique lab identity: {username}");
    println!("[!] This creates persistent resources. No automatic deletion.");
    let status = Command::new("hurl")
        .args(["--test", "--variables-file", ".secrets/hurl.env",
               "--variable", &format!("test_username={username}"),
               "--variable", &format!("device_external_id={device}"),
               "tests/provision-fido.hurl"])
        .status();
    match status {
        Ok(s) if s.success() => { println!("[+] SCIM FIDO pre-enrollment checks passed."); ExitCode::SUCCESS }
        Ok(s) => { eprintln!("[-] Hurl failed: {s}"); ExitCode::FAILURE }
        Err(e) => { eprintln!("[-] Could not execute hurl: {e}"); ExitCode::FAILURE }
    }
}

Run the project:

hx tests/provision-fido.hurl
cargo run

Each invocation creates persistent lab resources. There is no automatic deletion; record the test user and device identifiers from your authorized tenant’s audit trail and apply its cleanup policy.

Finish with an actual FIDO security key

At the end of this test, the device remains PENDING. A tenant administrator must have configured the HID IdP’s FIDO enrollment workflow, including its enrollment-protection mechanism. The user then completes the browser-based WebAuthn ceremony with a physical security key or supported passkey. The server verifies the registration and stores the corresponding public-key credential.

For device-bound assurance, consider deviceBinding: required, user verification, allowed AAGUIDs, and verified attestation as appropriate to the deployed HID workflow and authenticator capabilities. Do not claim a user is FIDO-enrolled merely because the SCIM device has an owner.

The productivity gain: fewer hidden steps

Helix keeps the source readable. Hurl makes expectations executable. Rust makes the sequence repeatable. Together they turn one-off requests into an integration test that can be reviewed in Git and rerun by another engineer.

A failed assertion points to the exact lifecycle step that needs investigation. Unique usernames avoid SCIM conflicts between runs. Explicit configuration separates the test logic from tenant credentials. The same files can later be incorporated into CI, provided that secrets, test-tenant permissions, cleanup, and reporting are handled appropriately.

This is not a claim that a terminal replaces every API tool. It is a practical way to reduce context switching and hidden state while preserving the HTTP requests as plain text. For identity systems, where authorization, auditability, and reproducibility matter, that is a meaningful productivity improvement.

Closing thoughts: the shell brings it together

What I like about this approach is that each tool does one job well. Helix keeps me close to the files I am editing. Hurl turns readable HTTP requests into tests with explicit expectations. Rust handles the small amount of orchestration needed to make each run consistent. And the shell ties everything together without another layer of clicking through screens.

The real advantage is not replacing Postman for the sake of it. It is having a project I can open, understand, change, and run again. Requests and assertions live in plain text, changes are visible in Git, and a failed step is easier to investigate. There is less to remember between sessions—and less hidden configuration for the next engineer to discover.

HID Authentication Service makes a useful example because an identity lifecycle involves more than a single API call: obtaining a token, creating a user, assigning a pending FIDO device, and checking the result. But the same pattern applies to other APIs: payment integrations, provisioning services, inventory systems, internal platforms, or a small service I am developing myself. The endpoints change; the workflow stays familiar.

For me, that is what terminal-first productivity means. Use simple tools that work together, keep the test readable, and make it easy to repeat the work tomorrow.
