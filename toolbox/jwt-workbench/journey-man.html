NAME

oidcflow — a small, non-executable text format for visualizing OpenID Connect authentication exchanges in JWT++ Debugger.

This is a visualization description, not a request runner, packet capture, Hurl interpreter, or proof that an implementation conforms to OIDC.

SYNOPSIS

Open How Login Works → Custom trace. Download the template, edit it using a text editor, then upload a .oidcflow or .txt file. Alternatively, paste the trace into the editor and select Load. The current custom journey is replaced only after a successful parse; built-in journeys stay available.

FORMAT

# JWT++ OIDC trace v1
# title: Short journey name
# subtitle: Authorization Code + PKCE
# actors: Browser | Application | Identity provider | Authenticator

STEP | Application | Browser | Start sign-in | 302 GET /authorize | Send the browser to the authorization endpoint.
DATA | {"response_type":"code","scope":"openid"}

The first line must match # JWT++ OIDC trace v1 exactly. Include a title, subtitle, the exact four-actor declaration above, and at least two STEP records.

RecordMeaning
# title:Display title, up to 64 characters
# subtitle:Short description, up to 70 characters
# actors:Exactly the four supported actors in the documented order
STEP | from | to | label | operation | noteDirected exchange between two different actors. Labels up to 76 characters, operation up to 64, note up to 220
DATA | { ... }Optional JSON object associated with the preceding STEP; one per step

Supported operation prefixes: GET, POST, 302, 200, 400, HTTPS, WebAuthn, OIDC, and CIBA (case-insensitive). The importer checks the prefix, not the semantic correctness of the exchange. Use illustrative paths and values.

EXAMPLE

# JWT++ OIDC trace v1
# title: Sample login
# subtitle: Authorization Code + PKCE
# actors: Browser | Application | Identity provider | Authenticator
STEP | Application | Browser | Begin authorization | 302 GET /authorize | Redirect with state and PKCE challenge.
DATA | {"response_type":"code","scope":"openid","code_challenge":"REDACTED"}
STEP | Browser | Identity provider | Authenticate | GET /authorize | User authenticates at the provider.
DATA | {"method":"provider policy"}
STEP | Identity provider | Browser | Return authorization code | 302 GET /callback | Return a one-time code to the client redirect URI.
DATA | {"code":"REDACTED"}
STEP | Application | Identity provider | Redeem code | POST /token | Redeem the code with the PKCE verifier.
DATA | {"grant_type":"authorization_code","code_verifier":"REDACTED"}
STEP | Identity provider | Application | Return tokens | 200 JSON | Client validates the ID token and claims.
DATA | {"id_token":"REDACTED","token_type":"Bearer"}

For a known-good starting point, use Get template in the application. Keep protocol examples illustrative; never paste real authorization codes or signed tokens into a shareable trace.

MULTIPLE JOURNEYS

You may import up to 12 custom traces into the current browser tab. They appear in the Journey Library alongside the five built-in examples. Select a trace to inspect it, or remove an imported trace individually. Importing another file does not overwrite an existing trace.

An optional comment # workspace: Demo environment labels a project or tenant context (maximum 40 characters). Use aliases rather than real customer names, tenant IDs, or confidential identifiers. Journeys are held in browser memory only: refreshing or closing the page clears imports. Keep the original .oidcflow files for reuse; the application does not automatically save or synchronize them.

LIMITS & VALIDATION

File uploads accept only .oidcflow or .txt names. The parser applies a 32 KB UTF-8 size limit, a maximum of 100 lines, at most 12 exchanges, a minimum of two exchanges, and one JSON object (up to 2 KB of source text) per step. JSON nesting is limited to four levels and object field counts to 30 per object. Some control characters, angle brackets in text fields, and reserved JSON keys are rejected.

The format does not run scripts, issue HTTP requests, evaluate templates, or execute commands. These limits reduce exposure to malformed input, but they are not a substitute for a security audit. A syntactically valid trace is not necessarily an accurate protocol trace.

PRIVACY & NETWORK

Production traces? Mind your packets.

The custom journey importer reads and renders text in your browser. It does not upload the imported file to a JWT++ service. There is no account, telemetry SDK, or application backend in this standalone build.

But local-first is not the same as offline-only. The application can fetch bundled example fixtures, request OIDC discovery metadata from a provider URL you enter, and retrieve public JWKS keys for verification. Opening specifications, external sites, or an optional ChatGPT/Claude handoff leaves the application and may share the intentionally prepared prompt or destination information with that service. Your browser also fetches the site's HTML, CSS, and JavaScript from its hosting origin.

Before importing: replace real access tokens, ID tokens, authorization codes, refresh tokens, client secrets, session identifiers, personal information, tenant identifiers, and internal hostnames with placeholders. Avoid using production data even when the parser is local: browser extensions, device access, clipboard contents, and screenshots remain outside this tool's control.

Imported trace text is not automatically sent to an AI assistant. Use the separate, deliberate AI handoff only after reviewing its sanitized brief. For sensitive production investigations, prefer representative synthetic traces.

DIAGNOSTICS

When the importer rejects a trace, it reports the first detected problem and leaves the current journeys intact. Examples:

Packet gremlins stopped this trace:
Line 6: STEP needs five fields separated by |.
Nothing was loaded.
Packet gremlins stopped this trace:
Actor roles must match the four supported OIDC roles.
Nothing was loaded.

Check the exact header, separators, actor names, line count, JSON syntax, and operation prefix. The parser is strict by design. It prefers a clear refusal to inventing a plausible-looking protocol exchange.

DEVOPS & THE NEXT STEP

.oidcflow is a deliberately small, text-first interchange format. Keep synthetic traces in Git, review changes, and share examples between engineering and support teams without a server-side dependency.

Planned, not yet available: log2flow, a separate converter for reverse-proxy and API-server HTTP logs. The intended path is logs → log2flow → .oidcflow → JWT++. A trustworthy converter must redact sensitive data, correlate only supported exchanges, and distinguish observed events from inferred steps. This is a design direction, not an existing capability.

SCOPE

Current scope: illustrative OpenID Connect journeys such as Authorization Code + PKCE, token renewal, logout, and CIBA-related exchanges. The vocabulary is provider-neutral, so examples may describe HID Authentication Service, Keycloak, or Okta behavior where applicable. Importing a trace does not validate provider-specific capabilities or certify interoperability. Consult the provider's actual metadata and documentation for those details.

Hurl is for making HTTP requests; PlantUML is for diagrams. oidcflow intentionally does less: it describes a bounded set of exchanges that JWT++ can display and inspect safely.
