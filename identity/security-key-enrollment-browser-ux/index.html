Making Security-Key Enrollment Less Painful in Modern Browsers

A pragmatic look at reducing friction in FIDO2 security-key and smart-card enrollment, with Safari as a reference and a hands-on WebAuthn lab.

A physical FIDO2 security key is one of the strongest ways to establish device-bound authentication. Yet enrolling one in a modern browser can feel unnecessarily complicated. A user selects Add passkey, sees a choice of credential providers, perhaps a phone or QR-code prompt, and only eventually finds the physical key they already have in hand.

The security ceremony is important. The maze of choices is not.

My interest is in making the registration journey more predictable, especially when the intended authenticator is already known: an enterprise-issued security key or a FIDO2-enabled smart card inserted into a compatible reader.

The browser does not know the enterprise’s intent

Passkeys serve several legitimate use cases: synchronized credentials, built-in platform authenticators, hybrid phone authentication and removable security keys. Browser interfaces are designed to accommodate all of them. That flexibility becomes friction when an enterprise is deliberately enrolling a particular physical credential.

A user should not have to discover the right path through several dialogs. The relying party can express its intent before the browser starts the ceremony.

A security-key-first request

WebAuthn Level 3 defines client hints, including "security-key", to express a preferred authenticator experience. In registration, authenticatorAttachment: "cross-platform" provides a useful compatibility signal for older implementations. They are not the same thing: hints are UI preferences, while attachment selection constrains authenticator categories; neither identifies a particular smart card or proves enterprise issuance.

const credential = await navigator.credentials.create({
  publicKey: {
    challenge, // fresh challenge from the relying party
    rp: { id: location.hostname, name: "Example RP" },
    user: { id: userHandle, name: username, displayName: username },
    pubKeyCredParams: [{ type: "public-key", alg: -7 },
                       { type: "public-key", alg: -257 }],
    hints: ["security-key"],
    authenticatorSelection: {
      authenticatorAttachment: "cross-platform",
      residentKey: "preferred",
      userVerification: "preferred"
    },
    extensions: { credProps: true },
    attestation: "none"
  }
});

The example expresses a preference rather than an assurance policy. For enterprise deployment, decide whether discoverable credentials, user verification, and verified authenticator attestation are mandatory. residentKey: "required" can consume scarce authenticator storage; "preferred" is more flexible when a username-first flow and credential IDs are available. Likewise, userVerification: "required" is appropriate when policy requires PIN or another UV mechanism, but it adds interaction and can exclude older devices.

Client hints are not a guaranteed Safari shortcut. WebKit’s public issue tracker still lists implementation work for WebAuthn hints; test the actual installed Safari version rather than promising that a particular dialog disappears. Chrome and other browsers may render different choices from the same options.

Safari as a useful reference point

Safari 26.4 adds CTAP PIN/UV Auth Protocol 2 support and improves the handling of excludeCredentials when exactly one credential is excluded. Both matter for physical authenticators: modern PIN flows need interoperability, and exclusion lists should prevent redundant registrations. Neither change gives a website permission to suppress PIN entry, authenticator touch, or browser-controlled consent.

For a smart card, WebAuthn communicates with the FIDO2 authenticator application, not with its PIV/PKI or physical-access applets. The card must expose a supported FIDO2 transport through its reader and middleware path. A card that supports PKI alone will not become a WebAuthn security key because of a browser hint.

Reduce decisions, not security controls

The optimized journey should be simple: Register security key → present card or key → verify with PIN if required → touch or confirm → done. This is a target experience, not a promise of exactly five screens on every browser.

There are practical improvements beyond the options object:

  1. Use a dedicated Register security key action rather than a generic Add passkey entry point.
  2. Provision the card and its PIN before enrollment when managed issuance permits it.
  3. Use excludeCredentials to prevent registering the same credential twice, without treating it as a complete account-duplication control.
  4. Avoid unnecessary application-side confirmation screens; let the browser own the protected authenticator interaction.
  5. Capture browser, operating system, reader, transport, user verification and registration outcomes during testing. Optimize the number of decisions and the median completion time, not merely the number of clicks.

The assurance boundary still matters

hints: ["security-key"] does not prove that a hardware-bound, enterprise-approved credential was used. Cross-platform authentication can include hybrid mechanisms. For managed FIDO deployments, the relying party needs an enrollment policy, verified attestation where appropriate, device issuance records, credential lifecycle management and reliable server-side WebAuthn verification.

The browser cannot silently create a credential on a physical smart card, bypass a required PIN, or authorize an unattended touch. Those are deliberate security boundaries, not defects in the user experience.

Try the experiment

I built a Security-Key-First WebAuthn Lab to explore these choices on a real browser and authenticator. It supports registration and subsequent assertion verification using browser cryptography, with no backend required for the local demonstration. It is not an identity provider and must not be used as an authentication service for real accounts.

The experiment deliberately keeps the same three user-facing concepts: identity, enroll, authenticate. It exposes the relevant WebAuthn policy settings without hiding the authenticator’s security prompts.

Final thoughts

Hardware-backed authentication should be strong without being needlessly confusing. The opportunity is not to remove the security ceremony; it is to remove everything around it that does not contribute to assurance.

A better security-key experience is one where the user knows what to do, the browser knows what to prefer, and the relying party knows what it can actually trust.
